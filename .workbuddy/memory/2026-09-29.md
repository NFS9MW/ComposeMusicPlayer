## 第九轮：播放进度记忆 / 图标三处修复 / Linux 图标待诊断

### 1. 记住播放进度（用户报"重启后丢失播放进度与播放列表"）
歌单本身一直是持久化的，缺的是"停在哪首歌的哪个时间点"。做法与取舍见 MEMORY.md 的「播放进度记忆」一节。
要点：只存 `lastSongId` + `lastPositionMs`；不自动播放；不进 Compose 状态（位置每秒变十几次）；
放两个普通字段并用 `currentSettings()` 在写入时叠加；播放期间不写盘，靠 `resumeMoved` 让 `shutdown()` 补写。
**验证用数值而不是截图**：播放到 20160ms → 关窗落盘 20160 → 重启静置后仍 20160（未自动播放）→ 按播放 7 秒后关窗得 29760（证明从 20160 续接）。

### 2. `Song.titleFromFileName` 把整条路径当标题（用户报 Fedora 上显示 `/home/rhp/音乐/Finders X`）
`path.substringAfterLast("/\\")` —— 那**是两个字符的字符串 `/\`**，不是字符集，两个平台都匹配不上，函数静默返回整条路径。
于是无标签文件的标题变成完整路径，**列表也按路径排序**（全都挤在 `/` 或 `C:` 下）。
修复：`maxOf(lastIndexOf('/'), lastIndexOf('\\'))`。补 `SongNamingTest` 10 个用例——这两个函数此前**零覆盖**。
注意这个 bug 在两个平台都存在，Windows 上没暴露只是因为那里的文件有标签。

### 3. Windows 菜单图标"黑边 + 毛刺"
逐字节解析 ICO 后发现：`16/24/32/48/64` 这几档是 **8 位调色板格式，没有 alpha**，透明只靠 1 位掩码。
另外确认**图标数据里暗色边缘像素为 0**——黑边不是画出来的，是渲染产物：掩码排除的像素在 Windows 缩放时按黑色参与平均。
根因在 PNG：只有两种颜色的图被 ImageMagick 写成 `PaletteAlpha`(PNG8)，拿它做 ICO 自然是 8 位条目。
修复：`PNG32:` + `-type TrueColorAlpha`；修复后半透明像素从 0 变成 104~1016 个/档。

### 4. Fedora 44 KDE 图标异常——**未能定位，需要用户协助**
**当前模型会话读不了图片**（`Read` 返回 "does not support reading images"），只能用 ImageMagick 降采样成字符画间接看。
字符画显示那是一个**圆角方块**（不是我们的圆形图标），内部有斜带与橙色调块，下方有文字 → 判断是**回退/通用图标**，不是我们的图标渲染错了。

查 OpenJDK 源码得到的事实（已记入 MEMORY.md）：
- Linux 启动器图标用**绝对路径**：`Icon=/opt/<app>/lib/<名称>.png`，**不走** `xdg-icon-resource`（那个只用于文件关联的 MIME 图标）；
- `withDesktopFile` 的条件是「有文件关联 或 `--linux-shortcut` 或**配了自定义图标**」——我们配了 `--icon`，所以桌面项本来就该存在。
⇒ 配置层看不出问题，需要用户机器上的实际文件。已请用户提供 `cat /opt/composemediaplayer/lib/*.desktop` 等三条命令的输出。

### 另外

## 第十轮：随机播放顺序的持久化
用户反馈：开启随机后每次重启，播放列表都变了（剩余未播歌曲不保留）。

**关键洞察**：`playedInPass` 与 `upNext` 都是由「活动顺序（排列）+ 游标」推导出来的，而游标已由上轮的 `lastSongId` 恢复。
所以**只需把那份排列存下来**，两段列表就自然分对了，不必单独存"已播放/接下来"。

实现：
- `PlaybackQueue.restoreOrder(songIds)`：把存的列表当**建议**而非圣旨——已消失的 id 丢弃、之后导入的歌补到末尾、随机关闭时整个忽略。
- 调用时机：`rebuildDisplaySongs()` **之后**（它会给队列排序后的歌单并自己洗一次牌），`restoreResumePoint()` 之前。丢弃那次刚洗出的排列，代价一次 O(n)。
- 新增 `orderMoved` 标志，与 `resumeMoved` **分开**——排列可能在光标没动时改变（一轮播完重新洗牌）。
- **存放位置从头改为 library.json**：起初放进 `PlayerSettings`，实测 80 首时该字段占 settings.json 的 **92%**（10.5KB/11.3KB），1000 首约 126 KB。settings.json 的定位是"一小撮可读的偏好"，所以挪到 library.json 与歌曲数据同处。挪完 settings.json 回到 491 字节。

新增 5 个队列测试（18 → 23），覆盖：恢复后"已播放/接下来"两段一致、新导入补末尾、已消失 id 丢弃、随机关闭时忽略、空列表不动原排列。

实机验证：开启随机 → 播放 → 下一首 → 关窗（当前在下标 1，下标 2 是 X）；重启后**只按一次下一首**，落到 X。
字段移位后又完整跑了一遍，仍 PASS。两次都是先记录"下标 2 是哪首"再验证，若顺序被重洗几乎不可能命中。

## 第二轮（同日）：队列语义、改名、解码器瘦身、播放界面

用户的五点要求，逐条处理（第 5 点的形态先经用户确认：全屏沉浸式 + 退出按钮）。

根因：「已播放」是用游标位置 `active[0,cursor)` 推出来的，只在顺序播放时成立。

- `ComposeMediaPlayer` → **`ComposeMusicPlayer`**：settings.gradle / packageName / vendor / 窗口标题 / 配置目录 / `-Dcomposemusicplayer.*`；`AppPaths` 会在首次启动时把旧名下的曲库 `Files.move` 过来（只在目标不存在时搬）。`packageVersion` → **1.1.0**，MSI 按新名打包通过。

### 第三轮（同日）：播放界面精简 + 空格快捷键 + 几何背景

1. **去掉播放界面里的进度条与上一首/播放/下一首**。底部播放条一直在，同屏两份同样的控件没有意义；这一页只负责播放条给不了的东西——一张大到值得看的封面。`UNDER_THE_SLEEVE` 从 258dp 降到 116dp，封面随之变大（上限 480dp）。
2. **点播放条左下角封面/歌名/歌手改为 toggle**（`openNowPlayingScreen` → `toggleNowPlayingScreen`）。
3. **空格 = 播放/暂停**。踩了一个坑，值得记住：本应用里一切可点的东西同时是可聚焦的，而获得焦点的组件收到空格会「激活自己」。第一次写在普通 pass（`onKeyEvent`）里，点完歌曲行再按空格 → 那一行被重新触发，而不是暂停（截图里播放/暂停图标根本没变）。改成在 `onPreviewKeyEvent` 里拦截，并且**只在 `controller.searchFieldFocused` 为假时处理**——否则搜索框里打不出空格。焦点由 `SongList`/`SearchField` 通过 `onFocusChange` 上报（那个 `interactionSource` 本来就在跟踪焦点）。
   - 代价：聚焦的按钮不能再被空格激活（`Enter` 仍可），刻意取舍。
   - 实测：点歌曲行后按空格 → 图标从 ⏸ 变 ▶；聚焦搜索框后按空格 → 占位符消失、清除「×」出现（空格确实被输入了），播放状态不变。
4. **几何背景** `geometricBackdrop()`：两团径向光晕 + 一对同心圆环 + 一个旋转 18° 的方框轮廓，三种线宽层次。全部取主题色，**同一组 alpha 在深浅两种主题下重量大致相当**（M3 tonal 体系：深色下 primary 偏亮、浅色下偏深）；不 blur、不动画、不读状态，`drawWithCache` 保证渐变只在尺寸变化时构建。第一版 alpha 太保守（几乎看不见），加强后两种主题都实机确认。

## Windows 侧打包修复（同日）

用户报「项目复制到 Windows PC 后打包报错」。逐层剥下来是**三个独立问题**，只有一个在项目里。

### 1. 依赖解析被一个失效代理拦下（机器级）
`~/.gradle/gradle.properties` 里配着 `systemProp.http(s).proxyHost=127.0.0.1:7897`（Clash），当时没在跑 ⇒ 任何依赖解析都 `Connection refused`，而且被 Gradle 包装成误导性措辞（`It might be caused by SSL misconfiguration`），顺着那句查会查错方向。**Gradle 不读 `HTTP_PROXY` 环境变量**，只认 `systemProp.*`。
定位方式：`curl -x http://127.0.0.1:7897` 与 `--noproxy '*'` 各试一次，直连 200。

### 2. `cmp.packaging.javaHome` 指向 Linux 路径（**项目级的真 bug**）
`gradle.properties` 里写着 `/home/rhp/.gradle/jdks/jetbrains_s_r_o_-25-amd64-linux.2`——Fedora 侧为了绕开发行版补丁过的 JDK（jlink 拒绝从「已修改」的 JDK 构建镜像）而加的。Windows 把它解析成 `H:\…\composeApp\home\rhp\.gradle\jdks\…`，于是：
```
property 'jdkHome' specifies directory '…' which doesn't exist
```
**每个打包任务在动手之前就被 `checkRuntime` 的 `@InputDirectory` 校验拦下**，MSI 一个字节都没产出。

修复：
- `gradle.properties` 里那行**注释掉**，并把注释改写成「机器本地配置、放用户级文件」。实测 **`~/.gradle/gradle.properties` 优先于项目内那份**（用 `./gradlew properties` 看生效值验证）⇒ Fedora 侧把这一行挪进用户级文件即可，项目文件不再带机器路径。
- `composeApp/build.gradle.kts` 加存在性校验：指向不存在的目录就忽略、回落到 Gradle JVM（`Application.javaHome` 默认值就是 `java.home`），打一行 lifecycle 说明。⇒ 两台机器都不必改文件。

### 3. WiX 由插件下载，两半缓存各自独立（机器级）
`downloadWix` 从 GitHub 拉 `wix311-binaries.zip` 到 `~/.gradle/compose-jb/`；`unzipWix` 解压到 `<root>/build/wix311`。本机 `build/wix311` 是完整的，但那个 zip 不在 ⇒ 插件照样去 GitHub，在不通 GitHub 的网络下死在 `CONNECT refused by proxy: 502 Bad Gateway`。
根 `build.gradle.kts` 新增：`build/wix311` 同时含 `candle.exe`+`light.exe`+`darice.cub` 时跳过这两个任务（在干净机器上行为不变；想固定位置可用 `WIX_PATH` 环境变量）。

**配置缓存踩坑**：第一版把判定结果写成脚本顶层 `val`、在 `onlyIf { !它 }` 里引用 ⇒ `onlyIf` 是任务序列化状态的一部分，引用脚本属性等于拖进整个 script 对象，CC 拒绝序列化（`cannot serialize Gradle script object references`）。症状很阴：**MSI 已经写出来了**，构建才在收尾时 `BUILD FAILED`。改成把布尔值经 `forEach` 的局部变量按值传进 `onlyIf` 后通过。
