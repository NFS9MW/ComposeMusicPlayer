### 环境
- JDK 21.0.7 / Gradle 8.14.3。本机原本**没有 ffmpeg**。
- `scripts/fetch_ffmpeg.py`：钉住 BtbN 标签 `autobuild-2026-09-27-13-04`，抽 `bin/` 与 LICENSE 落到 `third_party/ffmpeg/<platform>/`。Windows 端（n8.1.3）已暂存成功，解压后 **159.5 MiB / 9 文件**（`avcodec-62.dll` 91MB）。**比预估的 60~70MB 大一倍多**，已如实修正 MEMORY.md。
- Linux 端拉取被本机代理阻断（`502 Bad Gateway`，连 range 请求也失败），**待办**：Linux 二进制只能在 Linux 机器上打包 Deb 时准备。

### 原型程序（`prototype/`，均为一次性验证代码，非应用代码）
- `PcmPlay.java`：解码探测 / seek 扫描 / 出声 / 暂停 / 反复回收。
- `SpawnTest.java`、`ConsoleProbe.java`：控制台窗口问题的两次尝试（像素比对不可靠，因桌面上有流式渲染）。
- `ConsoleWindowProbe.java` + `ConsoleControl.java`：最终用 JNA 枚举顶层窗口，做 A/B 对比与对照实验。

### 结论
1. **Windows 控制台窗口问题不存在。** 从 javaw 用普通 `ProcessBuilder` 起 ffmpeg，新增控制台窗口数 = 0。`CREATE_NO_WINDOW` 同样会启 conhost 但不出窗口，故「有 conhost」不是证据。对照实验（主动 `AllocConsole()`）证明检测器有效。
   ⇒ **放弃 JNA / CreateProcessW / 改 PE 头方案，就用 `ProcessBuilder`。** 省掉约 200 行原生互操作代码与一个依赖，也让 LGPL 合规更干净。
2. **seek 优秀**：偏差 ≤1ms，首字节 134~181ms 且与 seek 位置无关。
3. **解码 ≈800× 实时**；暂停时 ffmpeg 阻塞、CPU 0ms；10 次 kill→exit 均 0.2~0.4ms 无残留。
4. **`read` 会返回短块**（最小 4652B）⇒ 引擎必须按实际长度写 line。
5. 出声链路正常，实时节奏准确。

### 由结论导出的设计约束
- 首字节 ~150ms ⇒ 切歌有可感知空隙；无缝需提前预启进程（v1 暂不做）。
- 启动时预热 ffmpeg，把冷启动成本藏进启动画面。

## 修复：打包前置校验只认"任意平台"而非"目标平台"
用户指出：在 Linux 上打 Deb 时，如果只暂存过 `windows-x64`，构建会通过，但产出的安装包在 Linux 上没有解码器。

**顺带发现原实现还有第二个更隐蔽的缺陷**：校验挂在 `prepareAppResources` 的 `doFirst` 上，
而该任务在无可拷贝资源时会以 **`NO-SOURCE` 被跳过 —— 被跳过的任务不会执行任何 action**，
所以"完全没暂存 ffmpeg"这个最该拦住的场景反而绕过了校验。

**修法**：改为独立的 `verifyBundledDecoder` 任务（无 outputs ⇒ 永不 up-to-date），
由 8 个产出安装包/镜像的任务 `dependsOn` 它：`packageMsi/packageReleaseMsi/packageDeb/packageReleaseDeb/
packageDistributionForCurrentOS/packageReleaseDistributionForCurrentOS/createDistributable/createReleaseDistributable`。
**不挂 `run`** —— 开发运行允许没有解码器，好让应用内的诊断界面能被走通。

校验内容：按 `os.name` / `os.arch` 推出 `<os>-<arch>`（与 `fetch_ffmpeg.py` 的命名一致），
检查该目录下 `ffmpeg` / `ffprobe`（Linux 无 `.exe` 后缀）是否存在。

**已实测三条分支**：
- 平台匹配 → 通过并打印 `Bundled decoder: windows-x64 (159 MB)`（注意报的是**目录总大小**，
  因为 `ffmpeg.exe` 只有 540KB，大的是那些 DLL，报它没有意义）。
- 平台不匹配 → 失败，列出 needed / staged，并给出 `fetch_ffmpeg.py <platform>` 命令。
- 零暂存 → 失败，`staged: (nothing)`。
- 用 `-Dos.name=Linux` 模拟 Linux 主机验证了 Linux 分支：无 `.exe` 后缀，且**只在 Linux 时**追加
  `patchelf --set-rpath '$ORIGIN'` 提示。

测试方式：临时 `mv` 走平台目录再 `mv` 回来（同盘瞬时），已确认还原干净。
`createDistributable --dry-run` 确认校验在打包图中、不在 `run` 图中（且 dry-run 显示
`prepareAppResources SKIPPED`，正好佐证了上面那个 NO-SOURCE 隐患）。

## 第五轮优化：窗口最大化记忆 / 更换程序图标

### 1. 记住窗口是否最大化
先发现一个**会让这个功能失效的既有缺陷**：`shutdown()` 里只 `saveJob?.cancel()`，
于是"退出前 500ms 内的最后一次改动"必丢——而窗口最大化最常见的用法正是"最大化然后关掉"。
改为 cancel 后若有在途写入则同步刷写（`saveJob?.isActive` 判断，避免每次退出都重写整份曲库）。

第二个坑是**最小化**：最小化一个已最大化的窗口时，AWT extendedState 变成 `ICONIFIED`，
Compose 把它读成 `WindowPlacement.Floating`。照单全收就会在"点去别的窗口再从任务栏关掉"时丢掉最大化状态。
解法是仅在 `window.extendedState and Frame.ICONIFIED == 0` 时才记录（`Main.kt` 的 `ObserveWindowPlacement`）。

用新写的 `prototype/WindowDriver.java`（JNA 直调 Win32）跑通四条路径：
最大化→关→重启恢复最大化 ｜ 最小化后关（值仍为 true）｜ 取消最大化→false→重启窗口化 ｜ 最大化后 0.2 秒内退出仍保住 true。
`changeAndQuit` 那条是专门为验证退出刷写而加的——只有它能让"改动"落在防抖窗口之内。

### 2. 更换程序图标
源素材归置为 `assets/app-icon.svg` + `assets/app-icon.png`（原来是根目录的中文名文件；改 ASCII 名避免脚本在非中文 locale 上出问题）。
新增 `scripts/generate_app_icon.py`，用 ImageMagick 的 RSVG 委托栅格化，**逐级减半**出各尺寸（1024→16 一步缩会把小图标糊掉，已放大比对确认 16px 下音符仍可辨）。

三个输出对应三条加载路径：运行时窗口图标（composeResources 256px PNG）、Windows `.ico`（7 档）、Linux 128px PNG。
**关键发现**：Compose 1.13 的 `AbstractPlatformSettings` 只有 `iconFile`、没有 `iconDir`（javap 本机插件 jar 确认），
与 jpackage 21 的行为一致——Linux 的 `LinuxAppImageBuilder.ICON_PNG` 拒绝非 `.png` 结尾的路径，
`DesktopIntegration` 里也没有遍历目录/从文件名解析尺寸的逻辑，尺寸是读像素得到的。
所以 Linux 给单张 128px（在 jpackage 吸附的 16/22/32/48/64/128 列表内），给尺寸目录不会被读取。

验证：编译期 `Res.drawable.app_icon` 报 Unresolved reference——访问器是扩展属性，**除 `Res` 外还要 import `app_icon`**。
打包后确认图标确实嵌入 exe：IM 的 EXE 解码模块本机没装，改为解析 `.ico` 目录项、把每个条目字节在 exe 里做子串查找，7 条全中。

只查可见行会让按钮在"其余全是死链"时报告一切正常。已记入 MEMORY.md。

链路：`LibraryService.findMissingFiles()`（suspend，实现内 `withContext(Dispatchers.IO)`）→ `Playlist.removeSongs(Set)` 批量移除
→ 若正在播放的曲目失效则先 `stopPlayback()` → `coverArt.clear()` → `rebuildDisplaySongs()` → `scheduleSave()`。
只查存在性（`isFile`），不重读标签与封面；用"一被调用就报错"的 `MetadataReader` 桩把这个契约写进测试。

实机验证：删掉 3 个媒体文件后点刷新 → 提示「已检查 80 首，移除 3 首（文件已不存在）」，侧栏与表头 80→77，
队列「接下来」79→76，列表里那 3 首消失。验证用的 3 个文件事后已用 `generate_demo_media.py --filler 72` 重新生成。
新增 `prototype/Click.java`（单点点击，配合 1:1 裁剪定位），比复用会打字的 `InteractionTest` 更顺手。

### 2. 图标反色
用户的判断是对的，而且比预想更严重：源美术是**深色圆盘 + 镂空音符**，镂空处透出的是背景色，
所以在深色任务栏上圆盘与音符是**一起消失**的，不是变淡。做了六宫格对比（浅/深背景 × 原版/反色/反色+描边）确认。

反色做法：`assets/app-icon.svg` 的单个 `<path>` 里正好两条子路径（圆盘 + 音符，2 个大写 `M`），
脚本在第二个 `M` 处切开、分别填色，得到浅色圆盘 `#F1F0F6` + 深色音符 `#272636`。**只维护一份源矢量**。
- 正则用 `\sd="` 锚定空白，否则会命中 `p-id="..."` 里的 `d="`。
- 深色下清晰，浅色下圆盘近乎隐形、只剩深色音符，仍可读——刻意取舍，已向用户说明。
- 描边方案（给圆盘加轮廓以在浅色下保住剪影）实测可行但未采用：要缩放美术才不被画布裁掉，且 16–32px 下是亚像素。
- 重新打包后确认新 `.ico` 的 7 条条目仍全部嵌入 exe；标题栏 16px 处可见"浅底深音符"。

## 第七轮优化：工具栏图标的悬停提示

需求是给列表工具栏那四个图标（刷新、名称排序、添加文件、添加文件夹）加悬停文本说明。

**第一个坑：Material3 的 `TooltipBox` 在桌面端不响应悬停。** 先按标准做法用它实现，编译通过、无警告，
但实测——悬停 2 秒、按钮已出现悬停高亮（说明指针事件送达正常）——**提示始终不出现**。
反汇编 `BasicTooltipKt.handleGestures` 也没找到指针进入/离开的处理，说明它只服务长按。
顺带确认这个版本里经典的 `androidx.compose.foundation.TooltipArea` **已被移除**，没有现成的桌面替代。
结论记入 MEMORY.md，避免以后重复踩。新增 `prototype/Hover.java`（只悬停不点击，否则会把要拍的东西点没）。

**改为手写**：`hoverable` + `collectIsHoveredAsState` + `LaunchedEffect` 延迟 420ms
+ 自写 `PopupPositionProvider`（居中于按钮正下方，并按窗口尺寸夹紧——最后一个按钮不加夹紧会被屏幕切掉一半）。
气泡用 `inverseSurface` / `inverseOnSurface`，浅色主题自动得到深色气泡、深色主题得到浅色气泡，不需要按主题各写一套。
点击按钮时主动收起提示。约 60 行，全部稳定 API，无 experimental opt-in。

`IconAction` 新增可选参数 `tooltip`，**与 `contentDescription` 刻意分开**：后者供辅助技术朗读、可以是整句；
前者是扫一眼看的，必须短。其余调用点不传就完全不显示，行为不变。

验证：四个按钮逐一悬停截图确认文案与位置；浅深两种主题各截一张确认配色。47 测试仍全绿。

## 第八轮优化：悬停提示覆盖到全部图标按钮

用户确认把其余图标按钮一并加上。**最终 16 个 `IconAction` 调用点全部带 `tooltip`**：
列表工具栏 4（排序/刷新/加文件/加文件夹）、播放条 5（上一首/播放暂停/下一首/静音/队列开关）、
侧栏 5（主题切换/新建歌单/歌单重命名/歌单删除/收起状态下的展开队列）、队列面板 1（收起）、行内 1（从歌单移除）。

文案上做了一处统一：**"添加文件 / 添加文件夹"** 而不是用户口述的"从文件导入"——空歌单页面里那两个按钮的文案就是"添加文件/添加文件夹"，
同一个动作在两处用不同说法会让人以为是两件事。歌单行的 `contentDescription` 是"重命名"，提示给了更完整的"重命名歌单"。

**这轮最有价值的教训是定位方法。** 第一次悬停静音按钮没出提示，我一度以为实现有问题；
实际是我按缩放图目测的坐标偏了 30px（估 (1238,783)，真实 (1207,805)），悬停落空了。
可靠的读法：裁剪一个**已知范围的小区域**（`170x110+1180+748`），在裁剪图里按**占比**读位置再映射回原图——
占比与显示缩放无关。已写入 MEMORY.md。

另外踩了一个小坑：一次拼图命令没有 `cd` 到目标目录，三个中间文件生成在了仓库根目录，随后已移入 `.workbuddy/cache` 并确认根目录干净。
